## Gate order and smoke checks

The notebook first installs pinned non-Torch packages and checks Python, torch, torchvision, label order and GPU. Next it requires actual `APPROVED_SPLIT`, `APPROVAL`, Stage 4 inventory and current config paths. [`validate_cohort`](../src/nine_class_colab.py) calls the production Stage 6 approval validator and additionally requires a frozen protected test with all nine classes. The production validator checks source hashes, clinical labels and indices, approved statuses, exact-content groups, overlap groups, known lesion/patient IDs and publisher-test boundaries; it cannot certify the truth of a researcher's declaration. Missing files or the current unapproved inventory **stop the notebook**. The runner's `--validate-only` command is then run before any training call.

Only after approval does the notebook load one validation image twice to check `(3,384,384)` and deterministic preprocessing, then run a single batch-one GPU **inference** pass to check nine finite logits. It never uses the protected test for smoke or selection. A CPU or GPU mismatch, source-image hash mismatch, absent class, invalid approval, failed image decode or out-of-memory error stops before full training.

## GPU memory, OOM and effective batch

Stage 5 counted **58,087,667 trainable parameters**. Float32 parameter storage is about **221.6 MiB**; weights + gradients + Adamax's two state buffers are roughly **886 MiB** before activations, mixed-precision copies, batch normalization, allocator overhead and data tensors. The [T4 smoke result](NINE_CLASS_FINAL_TRAINING_READINESS.md) measured 4,262 MiB peak reserved for a synthetic batch-8 optimizer step. The [preflight helper](../src/nine_class_colab.py) reports actual runtime free/total VRAM and the batch plan; the notebook stops below 4 GiB free as a caution, then performs the approved validation-image inference smoke. A full clinical-data epoch is still unmeasured.

If CUDA OOM occurs during a future run, the runner has not silently lowered batch size. Inspect the last complete `last.pt` in Drive. To use a smaller microbatch, create a **new versioned config** (for example batch 2 × accumulation 16, nominal effective batch 32), rerun the approval and memory preflight, and start a **new run**. Changing the config changes its SHA-256; resuming the old checkpoint with a different microbatch/accumulation is rejected. Record the deviation and keep any BatchNorm policy explicit. Never alter the protected test or use it to choose a resource setting.
