## Focused identity review

The existing [BENIGN review server](../src/nine_class_benign_review.py) now serves `/strong`, using the same review code and ledger schema as the all-pair page. Its [page](../src/nine_class_benign_review.html) presents **all 19 source-test strong pairs first**, then `train/benign/1169.jpg`, then the remaining **63 source-train** strong pairs. It shows current progress, original full-resolution BENIGN and HAM photographs, exact paths and HAM image ID, original pHash/dHash/pixel metrics, geometry metrics, aligned overlay, amplified difference, landmark view, and source partition. Stage 3G images are aids; inspect the native originals and lesion-specific structures before judging. The source HAM `lesion_id` and diagnosis are displayed as source metadata, not proof of a Fanconic identity or a revised clinical label.

Each relation starts without a selected decision. `SAME_PHOTO`, `SAME_LESION`, `DISTINCT`, and `UNCERTAIN` remain human choices separate from automated categories. New `SAME_PHOTO` or `SAME_LESION` saves require at least 20 characters of visual explanation in the browser **and server**. A decision saves only that pair; it does not exclude an image. Reviewers can record a reason for disagreeing with the automated category separately. The prior unexplained human judgment is preserved as historical evidence and needs independent confirmation.

From the project root, a primary reviewer can reopen the existing ledger using `python src/nine_class_benign_review.py --port 8765` and open `http://127.0.0.1:8765/strong`. A genuinely independent second reviewer uses `python src/nine_class_benign_review.py --reviewer R2 --port 8768` and opens `http://127.0.0.1:8768/strong`. This creates `analysis/nine_class_recovery/stage3h/identity_reviews_R2.csv` only when launched and stores the second review separately from the existing primary ledger. The second review API omits Stage 3G columns that disclose the earlier human decision or timestamp, and starts with 429 explicitly unreviewed relations. Give the second reviewer access only to their interface during independent scoring; do not share the primary ledger or Stage 3G static gallery, whose CSV contains the prior decision. Reviewer codes are procedural labels; they do not prove two distinct humans without a study record. No second ledger has been created or filled during Stage 3H.

After both actual reviews, compare decisions by pair ID, preserve both ledgers, independently inspect disagreement and `UNCERTAIN` cases, and record any adjudication in a new separate record. Do not promote coherent geometry, a single unexplained choice, or a second choice alone to a verified identity. The 346 other candidate relations still need assessment before any BENIGN record can be declared free of known overlap.

## Blinded detector validation

The existing [blind server](../src/nine_class_blinded_validation_review.py) serves the frozen [40-case queue](../analysis/nine_class_recovery/stage3g/blinded_validation_queue.csv). A reviewer sees paired images and a case code. The browser API hides paths, lesion IDs, source partition, similarity scores, metadata relation, and the other reviewer's choices. Positive identity saves now require a written visual explanation. Start the two actual human reviews separately:

```powershell
python src/nine_class_blinded_validation_review.py --reviewer R1 --port 8766
python src/nine_class_blinded_validation_review.py --reviewer R2 --port 8767
```

These commands create `analysis/nine_class_recovery/stage3g/blind_decisions_R1.csv` and `blind_decisions_R2.csv` **only when launched**. Reviewers must not inspect the queue mapping, each other's ledger, or nonblind Stage 3G files until their own pass is complete. The 40 cases are provisional difficult nonmatches; different source lesion IDs alone do not verify visual nonidentity. No independent validation decision exists yet.

The new [reconciliation script](../src/nine_class_validation_reconcile.py) refuses to run until **both** 40-case ledgers are complete, schema and case order match, reviewer IDs differ, and positive identity choices have explanations. After genuine reviews, run `python src/nine_class_validation_reconcile.py --reviewer-a R1 --reviewer-b R2`. It writes `validation_reconciliation.csv`, a separate **blank** `validation_adjudication.csv`, and a source-hash summary under `analysis/nine_class_recovery/stage3h/`. Disagreements and concordant `UNCERTAIN` decisions remain unresolved; concordant positive or `DISTINCT` judgments still require source/visual checks. The script never writes back to reviewer ledgers and refuses to overwrite a prior reconciliation. An adjudicator must later document final judgments in the separate adjudication record, retaining both original reviews. No reconciliation output has been generated now.

Detector precision, recall, false-positive rate, and false-negative rate are **unavailable**. Independently verified hard negatives are zero, and the current positives are mainly byte-identical or controlled transformations. Establish verified positive and negative source identities, freeze any threshold on development examples, then use held-out verified examples for performance estimation. Do not treat the 40 provisional cases as ground truth.

The **seven HAM diagnostic classes and two broad source-defined binary classes are not mutually exclusive clinical diagnoses**. An HAM nevus can also be benign; a HAM melanoma can also be malignant. The network would learn a source-conditioned nine-label research task unless a later clinical ontology is independently established. Keep HAM diagnoses and the candidate source labels unchanged. Report per-source/per-class results and investigate source cues before interpreting accuracy clinically.

## Nine-class decision matrix

| Criterion | A — HAM + cited Fanconic after review | B — HAM + Fanconic + verified additional images |
| --- | --- | --- |
| Paper fidelity | Closest source-family match; local package structure and sizes match public Fanconic v4 metadata. Exact EG-VAN version, membership, and split are still unknown. | Preserves architecture and nine output names while changing binary cohort; must be labeled a nine-label adaptation. |
| Label compatibility | Fanconic labels remain as supplied, with unverified clinical derivation. | SIIM–ISIC 2020 has explicit melanoma-vs-mimicker scope. A compatibility decision is required before supplementing Fanconic broad labels; DICM-17K and ISIC 2019 do not directly solve this. |
| Independent cases and balance | Binary upper bounds 83 BENIGN/845 MALIGNANT after proposed exclusions; all 83 BENIGN records have strong HAM candidates. Confirming all 83 would leave zero eligible BENIGN. | Source totals are large, but **zero extra eligible cases have been demonstrated**. Count only licensed, label-compatible, ID-screened and photo-screened cases. |
| Protected test | Publisher source-test BENIGN upper bound 19, all strongly suspect; no defensible nine-class test yet. | A prospective protected test could be defined later, preserving Fanconic publisher-test restrictions and never using unlabeled official ISIC 2020 test as labeled evaluation. |
| Rights and leakage | Fanconic image-level rights and patient IDs unavailable; HAM photo overlap and 346 other relations unresolved. | Additional source brings rights, distribution-shift, patient/lesion grouping and cross-source photographic overlap work. ISIC 2020 metadata helps within-source grouping, but cannot establish Fanconic patient identity. |

**Recommended route:** finish independent review of the 83 strong pairs, then the remaining relevant relations, while requesting EG-VAN authors' exact binary package/version, split and duplicate policy. Preserve Option A as the closest paper-source comparison if enough independent BENIGN cases survive. In parallel, investigate official SIIM–ISIC 2020 metadata, rights, label scope and nonoverlap as the first Option B candidate. Choose the final nine-label cohort only after those gates. Nine-class implementation remains mandatory; **Stage 4 final manifest and splits are not ready**.
